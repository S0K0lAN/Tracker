# Focus Flow: руководство для агентов-разработчиков

## 1. Цель продукта

Focus Flow — персональный local-first таск-трекер для одного пользователя. Основной цикл:

> быстро записать задачу → увидеть её во времени и матрице → выполнить без зависимости от интернета.

Продукт объединяет девять рабочих маршрутов:

1. Сегодня — просроченные, запланированные и дедлайновые задачи дня.
2. Входящие — все задачи, включая задачи проектов; список и доска с переходом в отдельный календарь.
3. Проекты — создание и обзор проектных задач.
4. Календарь — недельная шкала, месячная сетка и диаграмма дедлайнов.
5. Матрица Эйзенхауэра — четыре квадранта по важности и срочности.
6. Поиск — задачи, проекты, теги и сохранённые фильтры.
7. Трекер привычек.
8. Корзина и архив.
9. Настройки, включая оформление и local-first синхронизацию.

Полный источник бизнес-правил: `docs/business-requirements.md`.

## 2. Текущее состояние MVP

Реализован браузерный React/TypeScript MVP:

- все девять маршрутов и fallback неизвестного URL;
- создание, редактирование, завершение, архивация, мягкое и окончательное удаление задачи;
- название, текст, проект, подзадачи, начало, дедлайн, важность, срочность, теги, напоминания и вложения;
- общий keyboard-friendly combobox, просмотр вложений и русскоязычный голосовой capture/parser;
- страница Сегодня, создание проектов и глобальный поиск;
- сохранённые фильтры с логикой тегов «любой / все»;
- сортировка и режимы Входящих «список / доска», календарное планирование вынесено в отдельный маршрут;
- корзина, отдельный архив завершённых и восстановление;
- понятный 25-минутный таймер фокуса с сохранением состояния и минут;
- автоматическая срочность по дедлайну и порогу 72 часа, ручное переопределение;
- неделя и месяц с deadline markers, а также диаграмма дедлайнов;
- матрица 2×2;
- создание и редактирование привычек с описанием, десятью векторными иконками и индивидуальным ритмом;
- темы, акцент, плотность, reduced motion, встроенные/пользовательский фон и синхронизация;
- schema v2, миграция и backup/recovery localStorage;
- localStorage-адаптер с import-backup/restore;
- OAuth Google Identity Services, скачивание/загрузка Drive, ручная и автоматическая синхронизация;
- универсальный реестр sync provider runtime с device-local конфигурацией;
- глубокая проверка snapshot, quarantine и безопасные URL вложений;
- реестр встроенных плагинов;
- unit/component и Playwright E2E-тесты;
- автоматический WCAG AA-аудит светлой и тёмной тем на desktop/mobile;
- windowed list и performance gate прокрутки списка из 500 задач.

Текущая реализация — проверяемая браузерная основа. Она ещё не является Tauri-сборкой для Ubuntu и не доказывает live OAuth-синхронизацию с Google Drive.

## 3. Быстрый запуск и обязательные проверки

Требуется Node.js 18.19 или новее.

```bash
npm ci
npm run dev
```

Приложение: `http://localhost:4173` (Playwright использует эквивалентный
loopback `http://127.0.0.1:4173`). Для live OAuth открытый origin должен точно
совпадать с Authorized JavaScript origin в Google Cloud.

Перед передачей любой существенной задачи:

```bash
npm test
npm run build
npm run test:e2e
```

Системный Chrome используется Playwright через `channel: "chrome"`. Если он недоступен, установите совместимый Chromium и явно обновите конфигурацию.

## 4. Архитектурные границы

```text
src/
├── components/              # общие UI-компоненты
├── pages/                   # продуктовые страницы и их проекции
├── domain/                  # модели и чистые бизнес-функции
├── state/                   # application state и команды MVP
├── core/
│   ├── storage/             # StorageAdapter и реализации
│   ├── auth/                # эфемерные OAuth-сессии
│   ├── sync/                # registry/runtime, snapshots, Demo и Google Drive
│   └── plugins/             # версионированный реестр расширений
└── test/                    # общая настройка тестов
```

Правила зависимостей:

- `domain` не импортирует React, браузер, Tauri, Google API или конкретное хранилище;
- страницы не вызывают Google Drive или файловую систему напрямую;
- внешнее хранилище, уведомления и синхронизация подключаются через контракты;
- вычисленную срочность не сохранять: сохраняются дедлайн, порог и ручное переопределение;
- неизвестные данные будущих плагинов нельзя молча удалять при миграции;
- OAuth-токены никогда не помещать в snapshot, localStorage или Google Drive;
- config-поля sync provider обязаны быть явно публичными; secret-поля должны
  передаваться только через authorization/runtime и защищённое хранилище;
- сторонний динамический JavaScript не выполнять до появления модели permissions и песочницы.

## 5. Бизнес-инварианты

### Задачи

- Название — единственное обязательное пользовательское поле.
- Важность: `low | high`, по умолчанию `low`.
- Без дедлайна срочность `low`.
- С дедлайном срочность становится `high`, когда осталось не больше `urgencyThresholdHours`.
- Порог по умолчанию — 72 часа.
- `urgencyOverride` всегда имеет приоритет над вычислением.
- Просроченная активная задача остаётся срочной.
- Дедлайн заменяет отдельное время окончания.
- Завершение не удаляет задачу; завершённые скрыты по умолчанию.

### Представления

- Входящие показывают все задачи, в том числе проектные.
- В календарную сетку попадает задача только с `startAt`.
- В диаграмму дедлайнов попадает задача только с `deadline`.
- Матрица содержит только активные задачи и всегда четыре квадранта.
- Привычки — отдельные сущности, не ежедневные задачи.

### Local-first

- UI не должен ждать сеть для локальных изменений.
- Ошибка Drive не откатывает и не уничтожает локальное действие.
- Демо-провайдер всегда явно подписан как демо.
- Реальную совместимость Drive нельзя заявлять без live smoke с отдельным тестовым OAuth-клиентом.

## 6. Google Drive

Текущий `GoogleDriveAdapter` использует Drive API v3:

- поиск в `spaces=appDataFolder`;
- файл `focus-flow-data.json`;
- создание multipart upload;
- обновление существующего файла media upload;
- bearer token внедряется снаружи и не сохраняется.

`GoogleDriveSyncRuntime` получает token через Google Identity Services,
пересоздаёт adapter после `401` и не сохраняет credential. Координатор умеет
скачивать remote, сравнивать ID/revision/hash, показывать конфликт, создавать
import-backup и повторно отправлять правку, сделанную во время upload.

Контрактные тесты находятся в `src/core/sync/GoogleDriveAdapter.test.ts`.

Для production необходимо:

1. Отдельные OAuth client ID для desktop и Android.
2. Authorization Code + PKCE.
3. Scope `https://www.googleapis.com/auth/drive.appdata`.
4. Системное защищённое хранилище токенов.
5. Серверно-атомарная precondition записи (текущая проверка version перед PATCH — best-effort).
6. Base snapshot для трёхстороннего merge.
7. Tombstone для удалённых сущностей.
8. Состояния auth-required, offline, conflict, 401/403/412/429 и retry.
9. Resumable upload для больших вложений.
10. Отдельный live smoke, создающий только тестовый объект и удаляющий только его.

Не расширяйте OAuth scope до полного доступа к Drive. Для пользовательского выбора файлов позже используйте Google Picker и `drive.file`.

## 7. Хранение и Tauri

`LocalStorageAdapter` — временный браузерный адаптер, а не выполнение требования о приватном JSON-файле.

Следующий `TauriJsonStorageAdapter` должен:

1. Читать versioned snapshot из приватного каталога приложения.
2. Валидировать schema version и выполнять миграции.
3. Писать новый snapshot во временный файл.
4. Сохранять предыдущий файл как `.bak`.
5. Атомарно заменять основной файл с учётом Windows.
6. Восстанавливаться из backup после повреждения.
7. Хранить вложения отдельно в `attachments/<content-hash>`, а в JSON — метаданные.
8. Не писать основной snapshot на каждый символ; использовать draft/recovery journal и debounce.

Перед добавлением `src-tauri` установите Rust, Cargo, WebKitGTK и системные зависимости Tauri 2. Для Android потребуются SDK/NDK/ADB. Не заявляйте платформенную готовность без реального build/install/launch smoke.

## 8. План дальнейшей реализации

### Этап A — усиление браузерного MVP

- Вынести state reducer в application-команды и нормализованные репозитории.
- Расширить contract-тесты schema v2, миграции и recovery повреждённого localStorage.
- Сделать undo после удаления и завершения.
- Добавить drag-and-drop задач с равноценным клавиатурным действием.
- Реализовать date-only без преобразования в UTC-полночь.
- Добавить preset reminders, системную доставку и permission UX.
- Вынести вложения из JSON в IndexedDB BlobStore.
- Повторить performance gate на 1000 задач и при необходимости настроить
  размер окна/высоту строк текущего windowed list.

### Этап B — синхронизация

- Добавить полноценный fake provider со сценариями offline/conflict/rate-limit.
- Ввести UUID устройства, entity revision, `deletedAt` и sync queue.
- Реализовать ETag/If-Match и трёхсторонний merge.
- Сделать постоянный индикатор ошибки и экран сравнения конфликтов.
- Добавить live smoke, запускаемый только при наличии секретов.

### Этап C — Ubuntu/Tauri

- Создать Tauri 2 shell без изменения доменных контрактов.
- Реализовать атомарное JSON-хранилище и отдельное хранилище вложений.
- Добавить безопасный OAuth redirect и secret store.
- Реализовать локальные системные уведомления.
- Проверить production build, установку, direct launch, offline и восстановление backup на Ubuntu 24.04.

### Этап D — Android и Windows

- Android: share target, `content://` вложения, фоновые ограничения уведомлений, отдельный OAuth client ID.
- Windows: атомарная замена открытого файла, WebView2, installer/update smoke.
- Общий набор contract-тестов должен проходить на каждом platform adapter.

### Этап E — продукт после MVP

- Повторяющиеся задачи и шаблоны.
- Сохранённые составные фильтры.
- Импорт Todoist/TickTick/Singularity/CSV и экспорт JSON/CSV.
- Расширенные привычки, архив и тепловая карта.
- Time blocking, focus mode и Pomodoro.
- Версионированный Plugin API v1 с permissions, namespaced storage и UI slots.

## 9. План тестирования и критерий «готово»

Для каждого изменения проверяйте:

- TypeScript/build без ошибок;
- domain unit-тесты с фиксированными часами;
- component-тесты основных действий;
- Playwright: прямой URL, переходы, Back/Forward и reload;
- отсутствие `pageerror` и необработанных `console.error`;
- доступное имя каждого интерактивного элемента;
- desktop 1440×900 и mobile 390×844;
- keyboard/focus и `prefers-reduced-motion`;
- local persistence после reload;
- для длинного списка: первая отрисовка < 2 с, p95 кадра < 40 мс и менее 8% кадров длиннее 50 мс;
- для адаптера — общий contract suite и error paths.

Запрещено считать кнопку рабочей только потому, что на ней есть `onClick`: тест должен проверять наблюдаемый эффект — URL, DOM, состояние или сохранённые данные.
