# Focus Flow: руководство для агентов-разработчиков

## 1. Цель продукта

Focus Flow — персональный local-first таск-трекер для одного пользователя. Основной цикл:

> быстро записать задачу → увидеть её во времени и матрице → выполнить без зависимости от интернета.

Продукт объединяет девять рабочих маршрутов:

1. Сегодня — запланированные и дедлайновые задачи дня.
2. Входящие — по умолчанию неразобранные задачи без проекта, начала и дедлайна;
   быстрый фильтр «Все» возвращает общий список. Доступны список и доска, а
   календарь — отдельным маршрутом общей навигации без shortcut из Входящих.
3. Проекты — создание и обзор проектных задач.
4. Календарь — год, месяц, неделя, три дня и день с маркерами дедлайнов.
5. Матрица Эйзенхауэра — четыре квадранта по важности и срочности.
6. Поиск — задачи, проекты, теги и сохранённые фильтры.
7. Трекер привычек.
8. Корзина и архив.
9. Настройки, включая оформление и local-first синхронизацию.

Полный источник бизнес-правил: `docs/business-requirements.md`.

## 2. Текущее состояние MVP

Реализован браузерный React/TypeScript MVP:

- все девять маршрутов и fallback неизвестного URL;
- создание, редактирование, завершение, архивация, мягкое и окончательное удаление задачи;
- отдельный режим просмотра существующей задачи с явными рабочими действиями;
- аварийный journal редактора с debounce, явным восстановлением/удалением,
  `Ctrl/Cmd+Enter` и очисткой после подтверждённой локальной записи;
- название, текст, проект, подзадачи, начало, длительность, дедлайн, важность, срочность, теги, напоминания и вложения;
- общий keyboard-friendly combobox, просмотр вложений и русскоязычный голосовой capture/parser;
- страница Сегодня, URL-addressable проекты и глобальный поиск с восстановлением
  запроса через Back/Forward;
- сохранённые фильтры с логикой тегов «любой / все»;
- сортировка и режимы Входящих «список / доска», календарное планирование вынесено в отдельный маршрут;
- корзина, отдельный архив завершённых и восстановление;
- понятный 25-минутный таймер фокуса с сохранением состояния и минут;
- автоматическая срочность по дедлайну и наследуемому порогу проекта (72 часа
  по умолчанию), индивидуальный порог задачи и ручное переопределение;
- год, месяц, неделя, три дня и день с внутридневными блоками по длительности
  и непрерывными диапазонными полосами `startAt → deadline` в секции
  «Весь день» временных видов и в месяце;
- матрица 2×2;
- создание привычек и редактирование названия, описания и одной из десяти
  векторных иконок; ритм считается по сохранённому `targetDays` только с
  локального календарного дня `createdAt`, но UI настройки расписания/цвета
  ещё нет;
- темы, акцент, семейство и масштаб шрифта, плотность, reduced motion,
  встроенные/пользовательский фон и синхронизация;
- schema v9, миграции schema v1–v8 и backup/recovery localStorage;
- инъецируемый StorageAdapter, сериализованная/coalescing очередь записей и
  localStorage-адаптер с import-backup/restore;
- переносимый JSON-export/import с preview, ограничением размера и отменой через import-backup;
- OAuth Google Identity Services, скачивание/загрузка Drive, ручная и автоматическая синхронизация;
- универсальный реестр sync provider runtime с device-local конфигурацией;
- глубокая проверка snapshot, ссылочная целостность, бюджеты размера/сложности,
  quarantine и безопасные URL вложений;
- минимальный in-process каркас реестра расширений без permissions, sandbox и
  готового Plugin API v1;
- unit/component и Playwright E2E-тесты;
- автоматический WCAG AA color-contrast gate светлой и тёмной тем на desktop/mobile;
- доступный keyboard/AT windowed list и performance gate прокрутки списка из 500 задач;
- CI для unit/build/E2E на pull request и `main`.

Текущая реализация — проверяемая браузерная основа. Она ещё не является Tauri-сборкой для Ubuntu и не доказывает live OAuth-синхронизацию с Google Drive.

## 3. Быстрый запуск и обязательные проверки

Минимально требуется Node.js 18.19. Для воспроизводимых проверок используйте
поддерживаемую LTS-версию. На Node.js 26 Vitest/jsdom конфликтует с
экспериментальным глобальным Web Storage Node; временный локальный запуск:

```bash
NODE_OPTIONS=--no-experimental-webstorage npm test
```

```bash
npm ci
npm run dev
```

Приложение: `http://localhost:4173` (Playwright использует эквивалентный
loopback `http://127.0.0.1:4173`). Для live OAuth открытый origin должен точно
совпадать с Authorized JavaScript origin в Google Cloud.

Перед передачей любой существенной задачи:

```bash
npm test
npm run build
npm run test:e2e
# Эквивалентный полный gate:
npm run check:full
```

`npm run check` включает только unit/component-тесты и build, поэтому E2E
запускайте отдельно. Playwright использует системный Google Chrome через
`channel: "chrome"`, а `npm ci` браузер не устанавливает. Если нужен bundled
Chromium, сначала явно измените конфигурацию/уберите `channel`, установите
браузер Playwright и заново подтвердите полный gate.

Повторная проверка 11 августа 2026 года подтвердила 184/184
unit/component-теста с указанным флагом Node 26 и успешный build. Попытка
запуска актуальных 34 E2E-сценариев 10 августа не дошла до assertions из-за
отсутствия системного Chrome.

Более новый полный локальный gate 24 августа 2026 года на Node.js 18.19.1:
439/439 unit/component-тестов, успешный build и 43/43 E2E-сценария. Оба
dependency audit (`npm audit` и `npm audit --omit=dev`) сообщили 0 известных
уязвимостей. Это датированный локальный снимок; актуальный CI теперь повторяет
unit/build/E2E gate на pull request и `main`.

Актуальный полный локальный gate 1 сентября 2026 года на Node.js 18.19.1:
508/508 unit/component-тестов, успешный build и 46/46 E2E-сценариев.

## 4. Архитектурные границы

```text
src/
├── components/              # общие UI-компоненты
├── pages/                   # продуктовые страницы и их проекции
├── domain/                  # модели и чистые бизнес-функции
├── state/                   # application state и команды MVP
├── core/
│   ├── storage/             # StorageAdapter и реализации
│   ├── auth/                # эфемерные OAuth-сессии
│   ├── sync/                # registry/runtime, snapshots, Demo и Google Drive
│   └── plugins/             # минимальный каркас реестра расширений
└── test/                    # общая настройка тестов
```

Правила зависимостей:

- `domain` не импортирует React, браузер, Tauri, Google API или конкретное хранилище;
- страницы не вызывают Google Drive или файловую систему напрямую;
- внешнее хранилище, уведомления и синхронизация подключаются через контракты;
- вычисленную срочность не сохранять: сохраняются дедлайн, порог проекта,
  необязательное индивидуальное переопределение порога и ручная срочность;
- неизвестные данные будущих плагинов нельзя молча удалять при миграции;
- OAuth-токены никогда не помещать в snapshot, localStorage или Google Drive;
- config-поля sync provider обязаны быть явно публичными; secret-поля должны
  передаваться только через authorization/runtime и защищённое хранилище;
- сторонний динамический JavaScript не выполнять до появления модели permissions и песочницы.

### 4.1. Распределение задач между агентами

При параллельной работе ведущий агент отвечает за декомпозицию, назначение
владельцев файлов, интеграцию результата и финальную проверку. Каждый дочерний
агент получает один ограниченный блок работы с наблюдаемым критерием готовности;
широкие формулировки вроде «улучшить приложение» сначала делятся по слоям.

Рекомендуемое распределение:

| Роль | Зона ответственности | Типичные файлы |
| --- | --- | --- |
| Ведущий / интегратор | План, границы задач, разрешение пересечений, итоговый diff, полный test gate, commit/push и GitHub issues | весь репозиторий только на этапе интеграции |
| Домен и данные | Бизнес-инварианты, модели, миграции, чистые функции и contract-тесты | `src/domain/`, модели application state |
| UI/UX | Страницы, компоненты, responsive-состояния, keyboard/focus, светлая и тёмная темы | `src/pages/`, `src/components/`, CSS |
| Платформа и интеграции | StorageAdapter, auth, sync provider runtime, Google Drive и plugins без утечки секретов | `src/core/` |
| QA / независимый ревьюер | Воспроизведение issue, негативные сценарии, component/E2E, accessibility и performance; по умолчанию не переписывает реализацию владельца | `src/**/*.test.*`, `e2e/`, отчёт о проверке |
| Документация / релиз | README, product docs, acceptance notes и соответствие изменений issue | `README.md`, `docs/`, `AGENTS.md` |

Правила координации:

1. До начала правок ведущий фиксирует для каждого агента scope, критерии
   приёмки, ожидаемые тесты и файлы, которые нельзя менять.
2. Один изменяемый файл одновременно принадлежит только одному агенту. Для
   общих файлов (`models.ts`, `AppContext.tsx`, `styles.css`, миграции) заранее
   назначается единственный владелец; остальные передают ему требования.
3. Агенты работают в общем рабочем дереве: нельзя откатывать, форматировать или
   перезаписывать чужие изменения. Неожиданное пересечение сразу передаётся
   ведущему.
4. Домен, UI и внешние адаптеры разделяются по архитектурным контрактам. Агент
   страницы не добавляет прямой вызов Drive, а агент синхронизации не переносит
   сетевое состояние в доменную модель.
5. Реализация и независимая проверка по возможности назначаются разным агентам.
   QA начинает изменяющие тесты после стабилизации публичного поведения либо
   работает до этого только в read-only режиме.
6. Дочерние агенты не выполняют commit, push, закрытие issue и другие внешние
   действия, если ведущий явно не делегировал именно это. Эти операции по
   умолчанию остаются у ведущего после полного test gate.
7. Перед передачей результата агент сообщает: изменённые файлы, реализованные
   сценарии, выполненные команды и их результат, известные риски и номера
   покрытых issues. Ведущий повторно просматривает общий diff и запускает
   обязательные проверки из раздела 3.

## 5. Бизнес-инварианты

### Задачи

- Название — единственное обязательное пользовательское поле.
- Важность: `low | high`, по умолчанию `low`.
- Без валидного дедлайна срочность не настраивается и не отображается; для
  матрицы и фильтров такая задача имеет эффективную срочность `low`.
- С дедлайном срочность становится `high`, когда осталось не больше эффективного порога.
- Каждая задача наследует порог своего проекта; проектный порог по умолчанию — 72 часа.
- Задача может явно переопределить наследуемый проектный порог.
- `urgencyOverride` имеет приоритет над вычислением только при валидном дедлайне.
- Дедлайн в прошлом сохраняет эффективную высокую срочность, но отдельная
  категория и визуальная индикация «просрочено» не используются.
- Необязательная плановая длительность хранится в целых минутах от 1 до 1440.
- Плановая длительность и дедлайн взаимно исключаются: задача может иметь
  только одно из этих полей.
- Новый или изменённый дедлайн можно сохранить только при валидном `startAt`;
  пока дедлайн задан, начало нельзя удалить раньше самого дедлайна.
- Дедлайн — крайний срок, а не время окончания календарного блока.
- Legacy-задачи только с дедлайном загружаются без потери данных: их обычные
  поля можно редактировать, а для изменения срока нужно добавить начало.
- Завершение не удаляет задачу; завершённые скрыты по умолчанию.

### Представления

- Входящие по умолчанию показывают только задачи системного проекта `inbox`, у
  которых нет ни `startAt`, ни `deadline`; фильтр «Все» показывает прежний
  общий набор. Завершённые задачи скрыты по умолчанию в обоих режимах.
- Во временную календарную сетку попадает задача с `startAt` без `deadline`;
  дедлайновая задача показывается только диапазонной полосой «Весь день».
- В неделе, трёх днях и дне высота блока с длительностью задаётся
  `plannedDurationMinutes`; блок не переходит локальную полночь.
- Каждая задача с `deadline` отображается непрерывной полосой от локальной даты
  `startAt` до даты `deadline` в секции «Весь день» недели, трёх дней и дня, а
  также в месяце, без дублирующего временного блока или обычной строки. При
  совпадении дат и для legacy-задачи без `startAt` полоса занимает один день.
- Календарь показывает активные и завершённые задачи; архивные и удалённые
  задачи исключаются.
- Матрица содержит только активные задачи и всегда четыре квадранта.
- Привычки — отдельные сущности, не ежедневные задачи.

### Local-first

- UI не должен ждать сеть для локальных изменений.
- Ошибка Drive не откатывает и не уничтожает локальное действие.
- Демо-провайдер всегда явно подписан как демо.
- Реальную совместимость Drive нельзя заявлять без live smoke с отдельным тестовым OAuth-клиентом.

## 6. Google Drive

Текущий `GoogleDriveAdapter` использует Drive API v3:

- поиск в `spaces=appDataFolder`;
- файл `focus-flow-data.json`;
- создание multipart upload;
- обновление существующего файла media upload;
- bearer token внедряется снаружи и не сохраняется.

`GoogleDriveSyncRuntime` получает token через Google Identity Services,
пересоздаёт adapter после `401` и не сохраняет credential. Координатор умеет
скачивать remote, сравнивать ID/revision/hash, показывать конфликт, создавать
import-backup и повторно отправлять правку, сделанную во время upload.

Контрактные тесты находятся в `src/core/sync/GoogleDriveAdapter.test.ts`.

Для production необходимо:

1. Отдельные OAuth client ID для desktop и Android.
2. Authorization Code + PKCE.
3. Scope `https://www.googleapis.com/auth/drive.appdata`.
4. Системное защищённое хранилище токенов.
5. Серверно-атомарная precondition записи (текущая проверка version перед PATCH — best-effort).
6. Base snapshot для трёхстороннего merge.
7. Tombstone для удалённых сущностей.
8. Состояния auth-required, offline, conflict, 401/403/412/429 и retry.
9. Resumable upload для больших вложений.
10. Отдельный live smoke, создающий только тестовый объект и удаляющий только его.

Не расширяйте OAuth scope до полного доступа к Drive. Для пользовательского выбора файлов позже используйте Google Picker и `drive.file`.

## 7. Хранение и Tauri

`LocalStorageAdapter` — временный браузерный адаптер, а не выполнение требования о приватном JSON-файле.

Следующий `TauriJsonStorageAdapter` должен:

1. Читать versioned snapshot из приватного каталога приложения.
2. Валидировать schema version и выполнять миграции.
3. Писать новый snapshot во временный файл.
4. Сохранять предыдущий файл как `.bak`.
5. Атомарно заменять основной файл с учётом Windows.
6. Восстанавливаться из backup после повреждения.
7. Хранить вложения отдельно в `attachments/<content-hash>`, а в JSON — метаданные.
8. Не писать основной snapshot на каждый символ; использовать draft/recovery journal и debounce.

Перед добавлением `src-tauri` установите Rust, Cargo, WebKitGTK и системные зависимости Tauri 2. Для Android потребуются SDK/NDK/ADB. Не заявляйте платформенную готовность без реального build/install/launch smoke.

## 9. План тестирования и критерий «готово»

Для каждого изменения проверяйте:

- TypeScript/build без ошибок;
- domain unit-тесты с фиксированными часами;
- component-тесты основных действий;
- Playwright: прямой URL, переходы, Back/Forward и reload;
- отсутствие `pageerror` и необработанных `console.error`;
- доступное имя каждого интерактивного элемента;
- desktop 1440×900, промежуточная ширина 1024×900 и mobile 390×844;
- keyboard/focus и `prefers-reduced-motion`;
- local persistence после reload;
- для длинного списка: первая отрисовка < 2 с, p95 кадра < 40 мс и менее 8% кадров длиннее 50 мс;
- для адаптера — общий contract suite и error paths.

Запрещено считать кнопку рабочей только потому, что на ней есть `onClick`: тест должен проверять наблюдаемый эффект — URL, DOM, состояние или сохранённые данные.

## 10. Product/UX-ориентиры

- Todoist: быстрый захват, progressive disclosure, AND/OR фильтры, несколько напоминаний.
- Яндекс Трекер: декомпозиция, сильный поиск, вложения и несколько календарных представлений.
- SingularityApp: отдельные плановая дата и дедлайн, календарь + привычки, offline-first.

Не переносите корпоративную сложность Яндекс Трекера, полноценный marketplace или все режимы референсных приложений в ближайший MVP. Сначала стабилизируйте основной task loop и данные.
